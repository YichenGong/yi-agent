# desktop（Tauri GUI）

## 模块说明

`desktop/` 是 yi-agent 的原生桌面应用，基于 **Tauri 2.x**（原生 OS webview）+
**React 19 + TypeScript + Tailwind CSS v4 + Vite** 前端。Rust 后端是一个薄桥接层，
**不含任何 agent 逻辑**：它只负责管理 `yi-agent app-server` sidecar 子进程的生命周期，
并在其 stdio 与前端之间转发 **JSON-RPC 2.0**（JSONL 分帧）帧。前端只依赖线协议
（`desktop/src/lib/protocol.ts`）；该线协议**不再手写镜像**，而是由 Rust 单一真源
（`yi-agent-rs/crates/yi-agent-app-server/src/protocol.rs`）经 **ts-rs** 生成到
`desktop/src/lib/generated/`，`desktop/src/lib/protocol.ts` 只做再导出。

`desktop/` **不是** `yi-agent-rs/` cargo workspace 的成员，独立构建。Rust workspace
不受本模块影响：`cargo test -p yi-agent-app-server`（397 个测试）与
`cargo test -p yi-agent-runtime`（全绿）仍全绿。

- **Task 3**：壳租约与项目 `lifecycleReady` 已接通真实租约。guardian 侧新增 `managed_channel_authority` 用例锁住了三条边界：持 Business 租约的客户端只能开绑定到**自己** owner 的通道（`a_business_lease_opens_a_channel_bound_to_its_own_owner`）、LeaseOnly 观察者开通道被拒（`a_lease_only_observer_is_refused_a_channel`）、已释放的客户端再用旧 grant 开通道被拒（`a_released_client_cannot_open_a_channel`）。即 `held`（拿得到租约）与 `ready`（租约仍被守护者承认）是两件事，任何一环拿不到都必须让启动停在那里。证据：`cargo test --all-features -p yi-agent-supervisors`（453 passed）。

- **Task 4**：逐会话 root 授权、attach 与 foreground driver 落地。每个会话按 `thread:<key>` 独立授权（root id 由 capability 解析，不是拿项目路径冒充 root id），授权后 attach 得到的 root id 必须与授权里的一致，否则拒绝（`the authorized root is ... but the daemon attached ...`）；guardian 只用能力换 root，不允许从项目路径伪造授权（`foreground_root_lifecycle_public_key_cannot_retrieve_capability`、`foreground_root_lifecycle_identity_does_not_create_a_root`）；tool channel 不能自行安装 authority（`foreground_root_lifecycle_tool_channel_cannot_install_authority`），bridge EOF 与静默都按失败处理而不是挂起（`foreground_root_lifecycle_bridge_eof_closes_admission`、`foreground_root_lifecycle_a_silent_bridge_times_out_instead_of_hanging`）。另一处真实缺陷同时修掉：受管 daemon 现在从 guardian ledger 取 `daemon_instance_id` 作为自己的 generation，不再自造一个——否则第一帧授权就会被判成 stale，永远接不上任何 root（`adopt_managed_authority` 用 Mismatch 明确报错，而不是逐个请求失败）。证据：`cargo test --all-features -p yi-agent-supervisors`（453 passed，含 `foreground_root_lifecycle` 全部用例）、`cargo test --all-features -p yi-agent-store`（含改造后的 `managed_attach_authority` 6 例，fixture 改为先开 coordinator 再按它的 generation 造 ledger）、`cargo test --all-features -p yi-agent-subagent --lib`（163 passed）。

- **Task 5**：TUI/headless 的 fail-closed 接线完成。顺序固定为 `prepare → register_business → heartbeat → authorize_root → attach_root → bind_driver → open_managed_channel → admit_turn`，真实进程用例逐行比对这个序列（`a_managed_headless_run_walks_the_startup_stages_in_order`）；任一步拒绝都让命令失败、且后续 stage 一个都不出现（`a_refused_managed_start_never_falls_back_to_an_embedded_daemon`）；没有声明 managed 的运行不得走这台门（`an_embedded_run_never_reports_a_managed_stage`）——这三条合起来才是「严格」：只把 managed 变严而让 embedded 保持原样，缺一条就会把用户送到一个没人担保的 runtime 上。受管登记用 `FrontendLeaseHandle::register_required`（拿不到即错），不用 `.ok().flatten()` 兜底；embedded 路径保留历史行为，包括 guard 正在服务时仍从 lease 取 owner（`a_headless_runs_tool_processes_are_owned_by_that_run` 覆盖）。受管的 spawn owner 与授权 root 现在收在一个 `ManagedRunOwnership`/`ManagedTuiStart` 里整体传递，不再用两个独立 `Option` 参数——分成两个参数时调用方可以只传其中一个，得到一个没有授权 root 的 managed spawner。证据：`cargo test --all-features -p yi-agent`（1058 passed）、`cargo test -p yi-agent --test managed_runtime_lifecycle`（12 passed/1 ignored）、`cargo test -p yi-agent --test frontend_runtime_lease`（9 passed）、`cargo clippy --all-targets --all-features -- -D warnings` 干净。

- **Task 6**：旧 runtime 的只读证据探测落地。新模块 `yi-agent-supervisors/src/lifecycle/legacy_evidence.rs` 的每个观测都是三态 `Observation`（`Verified`/`Unknown`/`Contradicted`），而不是默认 true 的 bool——「查过且为真」与「从没查过」必须能分开，否则迁移会拿着一个猜出来的结论当清白证明。身份证明走内核而不是运行时自述：`LOCAL_PEERPID`/`getpeereid` 拿 socket peer，`proc_pidinfo` 拿启动时间与可执行路径，再比对摘要——PID 会被系统回收，所以单凭号码相同不构成任何证明；任何一步查不到都返回 `Unknown` 并写明缺哪个事实。`LegacyEvidence::automatic_takeover_allowed()` 是全部条件的合取（身份已验证 且 scope/锁已证 且 standalone 且 复活路径全部已知 且 宿主支持冻结 且 已冻结排空 且 已证空闲），本 build 里 `admission.freeze` 永远不会被承认，因此它如实返回 `false` 并列出缺口，而不是假装可接管。`MigrationPreview` 的 token 短时、仅内存、绑定证据摘要，证据一变即失效；inspect/preview 全程只读——测试在隔离实例目录上前后做全量快照比对（含 runtime 目录不存在的情形），并断言没有创建任何文件。证据：`cargo test --all-features -p yi-agent-supervisors --test runtime_migration`（32 passed，其中证据层 17 例）、`cargo test --all-features -p yi-agent-supervisors`（470 passed）、`cargo test --all-features -p yi-agent-store` 与 `-p yi-agent-lifecycle`（519 / 123 passed）、`cargo clippy --all-targets --all-features -- -D warnings` 干净。

- **Task 7**：持久迁移编排、退役 gate 与锁序落地。新模块 `yi-agent-supervisors/src/lifecycle/migration_operation.rs` 把一次迁移写成七个可观测阶段（`Accepted → SelfHealFrozen → WatchmanRetired → LegacyStopped → ManagedConnected → Completed / Failed`），每个阶段先原子写日志（temp-write + fsync + rename + 父目录 fsync、目录 0700、文件 0600）再做副作用，所以记录永远落后于事实而不会领先——「先写 Accepted 再动手」由 `the_accepted_record_is_written_before_any_side_effect` 与「Accepted 之前崩溃零写入」`a_crash_before_accepted_writes_nothing` 两例夹住。三条拒绝语义各有用例：截断/损坏日志**拒绝读取**而不是当成「无记录」（`a_truncated_journal_is_refused_rather_than_read_as_absent`）、同一 operation id 再次 confirm 直接返回已有记录且**不重复 stop**（`the_same_operation_id_returns_the_existing_result`）、stale preview 与跨 scope 证据一律拒绝且零副作用（`a_stale_preview_cannot_authorise_a_migration`、`evidence_from_another_scope_cannot_authorise_this_one`）。锁序按 spec 固定为 instance gate → scope guard，并以类型强制而不是靠记忆：`HeldScope` 拥有 `CoordinationGuard` 且 scope 只能经 `guard.scope()` 取得，因此「拿 A scope 的锁操作 B scope」编译不过；`ensure_managed_under_guard` 只接受已持有的 guard，绝不重新 acquire——`a_migration_never_waits_on_the_lock_it_already_holds` 用真实 bring-up 路径加 2s 预算断言不会自锁（自锁会耗满预算，实测 <900ms 就因「没有 guardian 可连」正常失败）。`ManagedConnected` 与 `Completed` 刻意分开：连接成功只代表 daemon 起来了，业务就绪还没确认；确认 ownership `ManagedConnected`（`a_crash_right_after_release_leaves_a_connected_operation_for_reconciliation`），`reconcile()` 只读、`confirm` 同 id 只回放记录，绝不会重跑 stop。失败路径同样有守卫：ack 被拒绝不写
