# Superpowers 看板 — 闭环接线设计（Plan 4）

**日期：** 2026-10-01
**状态：** 设计已确认，待评审
**模块：** 宿主监督能力（新 crate）+ daemon 监督循环 + 插件清单 + inbox 投递 + 两端实时看板 + `board-runner` 消费 inbox
**前置：** Plan 1（`board-core`）、Plan 2（`board-ipc` + daemon 自主会话）、Plan 3a（`board-runner` 插件进程）、Plan 3b（控制面 `yi-agent-board-ui` + TUI/Desktop 视图）已全部完成。

---

## 1. 背景与问题

Plan 1–3b 把看板的**全部组件**都造好了：卡片状态机、队列与时段并发日历、独立 IPC、
`board-runner` 插件进程（每 tick 原子写 `<state-dir>/board.json`）、宿主侧开关与视图数据、
两端组件。但**组件之间没有接线**：

- 插件进程**没有任何托管者**——必须手敲带参数的命令才起得来，没人守它、退出时也没人收；
- **没有「加入看板」的入口**——全仓唯一真正 `enqueue` 的调用者都在测试里，卡片永远进不了队列；
- 看板视图**不消费 `board.json`**——TUI `/kanban` 硬编码 `cards: Vec::new()`，生产代码无人调用
  `load_cards` / `parseBoard`，Desktop 组件未挂载到应用。

结果：能力齐全，但**今天没有任何入口能让看板真的跑起来**。本设计只做一件事——**打通闭环**，
让「提需求 → 排队 → 自动跑 → 看得见 → 等合并」这条链真正走通。

**闭环定义（本次要达到的端到端效果）：**

> 打开开关 → 宿主**常驻托管**拉起插件 → 在 TUI/桌面把一对 spec+plan「加入看板」→ 插件校验成对
> → 入队 → 按日历并发启动（预建 worktree、经既有 IPC 建自主会话跑 SDD）→ 插件原子写
> `board.json` → 两端**实时读**并显示卡片与「等待合并」→ 用户只在需要决策时介入。

## 2. 已确认的设计决策

| # | 决策点 | 结论 |
|---|--------|------|
| 1 | 插件怎么"活" | **宿主托管（方案 A）**：由宿主负责拉起/守护/停止插件进程 |
| 2 | 谁来守护（常驻者） | **daemon 托管（方案 A1）**：daemon 本就常驻；前端只翻开关+读看板。daemon 挂掉即停（既有部署前提） |
| 3 | 托管机制 | **插件清单（方案 A）**：清单声明命令/参数/开关键/state-dir；daemon 启动时扫目录，开关开则拉起、关则停。**不含看板专属逻辑** |
| 4 | 入队通道 | **投递目录（方案 A）**：宿主写 `<state-dir>/inbox/<id>.json`，插件每 tick 消费→校验成对→入队→删投递文件 |
| 5 | 闭环范围 | **两端一起（方案 B）**：TUI + Desktop 同时接入 |
| 6 | 实时性 | **轮询**（TUI 有 tick 循环；Desktop 固定间隔轮询）。本次**不做**插件→宿主的事件推送 |
| 7 | 「装/卸」定义 | 装＝放入二进制 + skill 目录 + 清单；卸＝删清单（daemon 随即停子进程）+ 删目录 |
| 8 | 并发上限 | 沿用既有任务级并发；默认 3，`kanban.toml` 可覆盖（含"不限流→10"的示例） |
| 9 | 合并决定权 | 始终留给用户；执行者**绝不自动合并**（沿用 spec，本次只把 `awaiting_merge` 显示出来） |

## 3. 架构

```
┌──────────── 前端（TUI / Desktop） ────────────┐
│  读 board.json → 实时显示卡片与状态            │
│  写 inbox/<id>.json → 「加入看板」            │
│  写 preferences.json → 开/关                  │
└──────────────┬────────────────────────────────┘
               │ 文件（无新增 IPC）
               ▼
┌──────────── daemon（常驻，即监督者）──────────┐
│  监督循环：扫 supervisors/*.json 清单          │
│    读该清单声明的开关键 → 决定 起/停            │
│    拉起子进程并守护（退避重启），退出时回收     │
│  仅认通用字段，不知道"看板"是什么              │
└──────────────┬────────────────────────────────┘
               │ spawn 子进程
               ▼
┌──────────── board-runner（插件，可装卸）──────┐
│  每 tick：消费 inbox → 校验成对 → 入队         │
│          按日历并发 → 预建 worktree            │
│          经既有 IPC 建自主会话并驱动           │
│          原子写 board.json                     │
└──────────────┬────────────────────────────────┘
               │ 既有 IPC（创建/驱动自主会话）
               ▼
          既有 daemon 会话运行时
```

**组件改动点：**

| 组件 | 形态 | 改什么 |
|------|------|--------|
| `yi-agent-supervisors`（新 crate，宿主） | 通用「按开关托管子进程」库 | 扫清单、解析两层开关、拉起/守护/按退避重启/退出时停子进程。**不含看板逻辑** |
| daemon（`yi-agent`） | 常驻进程即监督者 | `daemon serve` 起监督循环；开关变或清单变即增删子进程 |
| 插件清单 | `<workdir>/.yi-agent/supervisors/superpowers-board.json` | 声明命令、参数模板、开关键 `superpowers_board`、state-dir。**「已安装」＝清单存在** |
| inbox 投递 | `<workdir>/.yi-agent/board/inbox/<id>.json` | 宿主只写投递；插件消费后删除。**每文件单一写者** |
| `board-runner`（插件） | 既有二进制 | 加「消费 inbox」一步（`tick` 前先入队）；其余不变 |
| TUI `/kanban` | 既有 | 读 `board.json` 渲染实时卡片；新增 `/kanban add <spec> <plan>`；开关沿用 |
| Desktop | 既有组件 + 新 RPC | app-server 加 `board/list`、`board/enqueue`、`board/switch/read`、`board/switch/write`；挂载 `BoardView` + `SettingsPanel`，轮询 |
| `kanban.toml` 示例 | 随插件 | 落盘「周一至周五 00:00–09:00→10；09:00–24:00→3；周末全天→10」 |

## 4. 数据流（谁写谁读）

- 宿主 → `inbox/*.json`（投递）；插件 → `board.json`（状态）。**两个方向是不同文件，无并发写。**
- 开关：`preferences.json`（两层，项目覆盖全局，缺省关闭）。宿主 UI 与插件的解析规则
  **同构、各自有测试**（沿用 Plan 3b 已验证的做法）。
- 插件 ↔ daemon：只走既有 IPC（创建/驱动自主会话），**不新增协议**。
- **唯一的新接口**：Desktop 前端 → `bridge` → app-server 的 4 条 board RPC（见 §7.6）。

---

## 5. 装 / 卸 语义（精确）

- **装**：放入 `board-runner` 二进制、`kanban` skill 目录、以及清单文件
  `<workdir>/.yi-agent/supervisors/superpowers-board.json`。
- **卸**：删清单（daemon 随即停掉该子进程）+ 删其目录。**已在 daemon 中运行的会话照常跑完**；
  主程序功能不受任何影响。
- daemon 全程只认清单里的**通用字段**（命令、参数、开关键、state-dir），不知道「看板」是什么
  → 主流程保持干净。

## 6. 详细设计

### 6.1 监督器（新 crate `yi-agent-supervisors`）

- **清单 JSON 字段**（通用，不含看板语义）：
  `name`、`command`、`args`（支持 `{state_dir}` / `{workdir}` / `{runtime_dir}` 占位）、
  `switch_key`（如 `superpowers_board`）、`restart`（退避参数）、`cwd`。
- **循环**：每 N 秒重扫清单目录 + 重读各清单的开关键；对每个清单求「期望状态」
  （开关开且清单存在 → 运行）与「实际状态」，做差集增删。
- **守护**：子进程异常退出按退避重启（上限与间隔在清单里配）；不 panic。
- **回收**：daemon 退出时停止自己托管的全部子进程。
- **约束**：任何失败都只记 warning 并继续，绝不因一个坏清单拖垮 daemon。

### 6.2 daemon 集成

- `daemon serve` 启动后起监督循环（与既有会话服务并发）。
- 环境：把 `{state_dir}` 解析为 `<workdir>/.yi-agent/board`、`{runtime_dir}` 用既有
  `project_runtime_directory(workdir)`（即 `<workdir>/.yi-agent/runtime`，与既有 IPC 同址）。
- daemon 重启后重新扫描并按开关恢复监督（幂等）。

### 6.3 inbox 投递（宿主侧）

- 宿主「加入看板」时写 `<state-dir>/inbox/<id>.json`：`{id, spec_path, plan_path}`。
- 写入用 temp + rename 原子替换；id 用卡片 id 保证重复投递幂等（同 id 覆盖）。
- 宿主**不**直接改 `board.json`。

### 6.4 插件消费 inbox（`board-runner`）

- 每 tick 在推进队列前：扫 `inbox/*.json` → **校验 spec/plan 成对存在**（复用
  `board-core::promotion`）→ 通过则 `enqueue` 为 `queued` 并删除该投递文件；失败则
  移入 `inbox/rejected/` 并记录原因（不删，便于用户查看）。
- 校验判据是**文件存在**，而非模型声称完成（沿用 spec §9）。
- 幂等：已存在同 id 卡片时跳过并不重复入队。

### 6.5 TUI `/kanban`

- `add <spec> <plan>`：校验路径参数 → 写 inbox → 回显「已投递，等待插件入队」。
- 默认视图：调用 `state::load_cards(state_dir)` 渲染实时卡片行（状态/进度/证据）；空则显示空态。
- 卡片**状态**在 TUI 可见（含 `needs_you` / `awaiting_merge`）。
- 开关沿用现有 `on|off`（项目层）。

### 6.6 Desktop

- app-server 新增 4 条 RPC（薄封装既有逻辑，不引入新的业务规则）：
  - `board/list` → 读 `board.json`（等价于 `state::load_cards`）返回卡片数组；
  - `board/enqueue` → 写 `<state-dir>/inbox/<id>.json`；
  - `board/switch/read` → 返回两层解析后的开关与来源；
  - `board/switch/write` → 写项目层开关。
- 前端：把 `BoardView` + `SettingsPanel` 挂载进应用外壳（侧边栏/设置入口）；
  以固定间隔轮询 `board/list` 刷新。
- **本次交互仅限**：看板显示、入队动作、开关。不做卡片操作与详情（见 §7）。

### 6.7 日历配置示例

- 随插件提供 `kanban.toml` 示例与文档：工作日 09:00–24:00 → 3；工作日 00:00–09:00 → 10；
  周六/周日全天 → 10。（字段沿用 `board-core::calendar` 既有解析。）

## 7. 错误处理与降级

- 清单缺失/损坏 → 跳过该清单并记 warning，daemon 继续。
- 子进程启动失败/立即退出 → 记 warning + 退避重启。
- `board.json` 缺失/损坏 → 两端渲染空看板（沿用既有读取器行为）。
- `inbox` 条目校验失败 → 移入 `inbox/rejected/` 并写明原因，**不静默丢弃**。
- 开关关闭 → 只停止推进与监督，**不杀**已在 daemon 中运行的会话。
- 看板读取失败绝不影响宿主主流程。

## 8. 测试策略

- **监督器**：用**假子进程**（如 `sleep` 脚本）验证：开关开→起、关→停、崩溃→退避重启、
  daemon 退出→回收、坏清单→跳过。
- **inbox**：成对校验（存在/缺失/路径穿越）、消费后删除、重复投递幂等、拒绝入 `rejected/`。
- **两端读 `board.json`**：在 Plan 3b 同构测试基础上补「实时刷新」用例。
- **UI/RPC**：TUI `/kanban` 渲染与 `add`；Desktop 4 条 RPC 与组件挂载（jsdom 约定）。
- **端到端**：用假插件脚本跑「投递 → 出队 → `board.json` 变化 → 读端可见」。

## 9. 本次不做（Deliberate Non-Goals）

> 以下均为**有意延后**，不是遗漏。逐条记录「为什么本次不做 / 什么时候做 / 与本次的关系」，
> 供后续 Plan 取用。**本次实现不得引入这些能力，也不得为其预留半成品接口。**

### 9.1 卡片交互操作
- **内容**：插队/优先级调整、顺序重排、暂停/恢复、取消。
- **为什么不做**：状态机（`prioritize`/`pause`/`cancel`）已在 `board-core` 具备，缺的是
  「宿主→插件」的操作通道；本次只打通**入队**这一条最关键的投料通路，操作通道留一条一致
  的设计（同 inbox 语义的下行通道）到后续 Plan，避免本次把两条通道一起设计错。
- **与本次关系**：不冲突；后续可复用 inbox 目录式下行的同一模式。

### 9.2 卡片详情视图
- **内容**：spec/plan 链接、commit 列表、变更统计、验证结论、分支名（原 spec §10 的「卡片详情」）。
- **为什么不做**：这些证据来自 SDD 账本与 git，需要在插件侧聚合出额外字段并扩展 `board.json`；
  本次先把「状态可见」做出来，证据字段随后续一并扩展。
- **与本次关系**：本次 `board.json` 结构不变，后续**增量**加字段（读取器已容错未知字段）。

### 9.3 打开执行会话 / TUI 会话时间线跳转
- **内容**：从卡片直接跳到该会话的只读时间线（原 spec 的第一版降级项，本次仍不做）。
- **为什么不做**：TUI 目前只有单一根会话、无多会话读路径；Desktop 需要完整只读订阅通道。
  这两条都超出「闭环」最小范围。
- **与本次关系**：独立增强，依赖两端的会话读路径先就绪。

### 9.4 Web 配置页
- **内容**：`yi-agent web` 里"Superpowers 看板"一组，管理全局与项目两层开关。
- **为什么不做**：闭环不依赖 Web；本次两端已覆盖开关操作。
- **与本次关系**：后续在既有 web 配置框架内增量增加。

### 9.5 全局层开关的界面编辑
- **内容**：在 TUI/Desktop 里**编辑** `~/.yi-agent/preferences.json` 的全局默认。
- **为什么不做**：本次 TUI/Desktop 只**写项目层**，但**读**两层（项目覆盖全局已生效）。
- **与本次关系**：解析语义已就位，后续只加一处 UI 写入口。

### 9.6 事件推送（插件 → 宿主）
- **内容**：插件主动通知宿主状态变化（替代轮询）。
- **为什么不做**：本次用轮询即可满足"能瞄一眼"；推送需要新的插件常驻服务面，扩大装卸面。
- **与本次关系**：本次的轮询接口与后续推送**互不冲突**，可平滑替换。

### 9.7 插件自注册 / 独立服务
- **内容**：插件启动时经 IPC 向 daemon 动态注册；或插件自带 HTTP/socket 服务。
- **为什么不做**：与"独立可装卸 + 主流程干净"冲突（清单文件已是"已安装"的标志；投递目录
  已足够）。保持插件**没有常驻服务面**，装卸最干净。
- **与本次关系**：本次即最终形态，无需后续替换。

### 9.8 安装器 / 打包
- **内容**：一键把二进制 + skill 目录 + 清单装到位的脚本或打包产物。
- **为什么不做**：本次定义**手工/文档化**安装（§5 的明文步骤）；打包属发布工程，另行规划。
- **与本次关系**：后续 installer 只需执行 §5 的既定步骤。

### 9.9 跨项目看板
- **内容**：一个看板管理多个项目的卡片。
- **为什么不做**：沿用原 spec 决策 13；看板是 per-project 的（运行时/状态目录本就按项目划分）。
- **与本次关系**：不在路线图内。

### 9.10 看板内的需求讨论 / 草稿态
- **内容**：在看板里直接讨论需求、存草稿卡片。
- **为什么不做**：沿用原 spec 方案 A——讨论是高度交互且**不占队列资源**的过程；提升时两文件
  已存在。看板只承接"已决策完成的需求"。
- **与本次关系**：不在路线图内。

### 9.11 请求级限流计数
- **内容**：按 800 req/h 精确计数并据此限流。
- **为什么不做**：沿用原 spec——只做**任务级**并发；429 由既有退避兜底。
- **与本次关系**：不在路线图内；若将来需要，属 `board-core` 日历的增强。

### 9.12 自动合并
- **内容**：任何形式的替用户 `git merge`。
- **为什么不做**：沿用原 spec 决策 6——合并决定权**始终**留给用户。插件只把 `awaiting_merge`
  显示出来并给入口，由用户经 `finishing-a-development-branch` 走正规菜单。
- **与本次关系**：**永久非目标**。

### 9.13 不改既有语义
- **内容**：任务树、审核、交付、worktree 回收、既有 IPC 行为。
- **为什么不做**：本次是**接线层**，只**读取/复用**既有能力，不修改其语义。
- **与本次关系**：硬约束。

### 9.14 卡片进度百分比
- **内容**：卡片行显示如 `3/7 tasks` 的进度。
- **为什么不做**：`board.json` 无进度字段，进度需读 SDD 账本；本次 `progress` 恒为 `None/null`
  （Plan 3b 已如此）。
- **与本次关系**：与 §9.2 同批延后。
