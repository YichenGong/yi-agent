## 1. 用户场景与证据边界

用户报告：iOS App 的远程连接/配对页已经显示摄像头画面，但对准二维码、识别到码时出现黑屏。

### 1.1 已确认的代码缺陷

1. `desktop/src/lib/qrScanner.ts:131–133`：任何二维码解码成功后，先 `stop()` 停止视频轨道，再调用 `onResult(text)`。
2. `desktop/src/components/PairingScreen.tsx:183–191`：有效码回填 URL/配对码并启动异步兑换；没有立即关闭扫描器。
3. 同文件 `:151–173`：`scanning` 要到兑换结束的 `finally` 才置为 `false`；等待期间仍渲染 `:296–300` 的全屏 `bg-black` 扫码覆盖层。“配对中…”按钮在覆盖层背后的表单上，不是可见的进度反馈。
4. `desktop/src/components/QrScanner.tsx:14–19`：相机 effect 依赖 `onText`/`onError`；父组件每次渲染重建这两个函数，回填和 `busy` 更新会重新启动相机。
5. 测试接缝 `ScanHost` 已用 ref 转发最新回调，真实 `QrScanner` 却没有采用同样模式。仅测 `scan` 接缝不能覆盖生产路径的相机重启。

### 1.2 本地模拟结果

调查时通过 Vite SSR 加载真实 `PairingScreen` 与 `QrScanner`，在 jsdom 中替换相机 API、画布抓帧和 jsQR 解码；首帧产出合法测试二维码，兑换 Promise 保持 pending。未替换扫码 UI 组件或生产生命周期逻辑。

| 阶段 | getUserMedia 调用数 | 轨道 stop 调用数 | 兑换次数 | 扫码覆盖层 | 可见错误 |
|---|---:|---:|---:|---|---|
| 解码前 | 1 | 0 | 0 | 存在 | 无 |
| 有效码识别、兑换 pending | 2 | 1 | 1 | **仍存在** | 无 |
| 模拟兑换失败 | 2 | 2 | 1 | 关闭 | 无法连接服务器 |

既有验证命令：

```sh
cd desktop
npm test -- --environment jsdom src/lib/qrScanner.test.ts src/components/PairingScreen.test.tsx
```

调查时 2 个文件、29 条测试通过；这说明旧用例存在覆盖缺口，不代表问题不存在。临时探针未提交，实施时必须把上述生命周期判据转成持久回归测试。

### 1.3 尚未确认

- 本地模拟确认了停流后覆盖层残留和相机重复打开，**没有模拟 WebKit 像素输出，也没有证实真机 App 崩溃**。
- iOS 在停流/重新取流期间可能显示黑画面，这是与报告吻合的机制，但不能把可能性写成真机实测结论。
- 如果连顶部“返回”也消失、配对终止后仍完全无界面，应继续采集 WKWebView/系统日志，区分渲染异常、页面切换异常或 WebContent 进程退出。本文不承诺修复所有黑屏机制。

## 2. 目标与非目标

### 目标

- G1：有效码被接收后，第一次包含该结果的 React commit 即移除扫码覆盖层/预览；兑换仍 pending 时必须显示可见配对进度，不依赖网络响应才能退出相机页。立即成功/失败允许直接进入最终状态，不强制进度帧、最短停留或 `flushSync`。
- G2：同一扫描实例不因回调 identity 或父组件普通重渲染重新取流。
- G3：一次配对尝试只兑换一次；同一批重复结果不重复消费一次性码。
- G4：无效二维码保留预览、展示错误并继续扫描，不通过关/开相机实现“重试”。
- G5：取消或卸载后的相机异步结果不影响当前 UI，所有已获取轨道最终释放。
- G6：成功沿用现有凭据落盘/宿主切换；失败回到保留回填值的表单，可手输或重新扫码。

### 非目标

- 不引入原生扫码插件，不更换 Tauri scheme，不重写相机授权。
- 不修改二维码载荷、URL 生成规则、服务端协议、token/scope 格式或存储格式。
- 不修改 `defaultRedeem` 的中继/直连选择、网络超时或重试策略；不自动重试消费一次性码的请求。
- 不重构 `App.tsx`、不调整聊天页同步流程，不新增遥测系统。
- 本轮交付经过反复审查的 spec 与实施 plan；实现、iOS 打包/发布均不在本轮内。

## 3. 方案比较与决定

| 方案 | 收益 | 缺口/代价 | 决定 |
|---|---|---|---|
| A：有效码回调只加 `setScanning(false)` | 最小改动，去掉等待中的黑色覆盖层 | 不解决回调依赖重启；无效码仍停流；旧异步回调仍可污染下一轮 | 不单独采用 |
| B：退出扫码层 + 稳定生命周期 + 显式结果接收契约 | 同时解决停流后页面残留、重复取流和无效码重试；修改限于前端扫码链 | 增加少量结果契约和生命周期测试 | **采用** |
| C：原生扫码控制器 | 可绕开 WebView 相机兼容性问题 | 引入插件、权限/展示/构建链变化，超出已确认根因 | 本次不采用 |

保持现有 `scanning`/`busy` 状态，不另引入全局状态机。新增实例局部 attempt ref 在一次尝试的整个 pending 期间持有准入，状态占用发生在任何回填、错误修改或第一次 `await` 之前；它同时用于忽略页面离开后的迟到兑换结果，不是第二份 UI 状态。

## 4. UI 状态与数据流

### 4.1 状态表

| 状态 | scanning | busy | 用户看到什么 | 可执行动作 |
|---|---|---|---|---|
| 表单 | false | false | 地址、码、设备名及既有错误 | 手输配对、扫码；重配场景可返回 |
| 扫描 | true | false | 预览、安全区内的返回按钮、二维码错误提示 | 扫码、返回表单 |
| 配对中 | false | true | 回填后的表单、进度提示；**无相机覆盖层** | 禁止重复提交、扫码或编辑；传有 `onCancel` 的重配页仍可返回 |
| 成功 | false | true → 卸载/收尾 | 宿主切换到现有主界面 | 沿用现有宿主逻辑 |
| 失败 | false | false | 保留回填值的可编辑表单、现有失败文案 | 修正输入、重新提交或重新扫码 |

硬不变量：`busy === true` 时不得渲染扫码覆盖层；不能出现 `scanning && busy` 的可见状态。

### 4.2 有效二维码

1. 先检查当前组件/扫描实例是否仍有效、是否已有 pending 尝试；已有尝试则接受停机但完全忽略新文本，不回填、不修改错误、不再次兑换。
2. 解析二维码，得到有效的 `{relay, code}` 后，由统一同步准入入口占用本次尝试。`parsePairUri` 是同步纯函数，不读写状态、不调用外部回调、不 `await`，因此检查、解析、准入之间不会让出执行权；非法码不占用准入。进入合法尝试时才清空旧二维码错误。
3. 同一同步处理链中关闭扫码状态、回填字段并置 `busy=true`，随后启动现有兑换逻辑。不得在关闭扫码前等待网络；准入与回填顺序不得反过来。
4. 组件卸载清理与扫描器停机均必须幂等，不能因双重清理多次通知错误。
5. 默认兑换成功后，在同一同步块中检查尝试仍有效、持久化凭据、调用现有 `onPaired`，三者之间不得新增 `await`/定时器。调用 `onPaired` 前也核对 attempt，避免注入存储实现的同步重入继续通知已退出宿主；已发生的注入存储副作用不承诺回滚。注入 `onSubmit` 时继续由宿主接管落盘，`await onSubmit` 后只在尝试有效时通知宿主。
6. 失败且尝试仍有效时保持回填值，沿用“配对码无效或已过期……”/“无法连接服务器”的分类。
7. 本次有效尝试结束释放准入，恢复表单能力；失效尝试的 `finally` 不改 UI、不释放别的尝试。不会自动重新打开相机。

### 4.3 配对进度

- 表单增加可见 `role="status"` 提示。
- 扫码发起时文案为“已识别二维码，正在连接桌面…”；手输发起时为“正在连接桌面…”。发起来源只影响文案，不影响协议。
- 提交按钮保留“配对中…”的既有 busy 文案；输入项、扫码/重复提交在 busy 期间禁用或隐藏；输入 onChange/扫码入口还要检查同步 attempt ref，不能只依赖尚未提交的 `busy`。传有 `onCancel` 的返回按钮仍可用。
- 提示与成功/失败同步收敛：busy 结束必须卸载配对进度节点，失败使用 `role="alert"`，不得只改进度文本而保留旧节点。宿主 `notice` 已使用 `role="status"`，因此配对进度必须另带 `aria-label="配对进度"`，测试通过该名称定位，不假设页面只有一个 status。
- 不再放全屏黑色进度蒙层；不新增视觉稿或与本修复无关的动效。
- busy 期间不新增网络取消能力；保留重配返回但明确其语义是离开本地页面，详见 §4.5。

### 4.4 无效二维码

- 解析失败显示既有“不是有效的配对二维码”，留在扫描层并继续解码。
- 不兑换、不停轨道、不重新取流。
- 从无效二维码移向有效配对码，必须能在**同一相机实例**内完成配对。
- 无效提示沿用现有安全区内展示；用户仍可随时返回表单。

### 4.5 返回、卸载与现有网络边界

- 扫描层“返回”先使该扫描回调失效，再关闭扫描层；不开启兑换。
- 重配表单“返回”在 busy 时仍可点：调用 `onCancel` 前先使当前尝试失效，不清理已有持久配置。组件卸载也必须使尝试失效。
- 失效后到达的默认兑换结果不得落盘、调用 `onPaired`、更新错误/进度或影响新挂载的配对页；需要在 `await` 后、写配置前检查 attempt identity 和有效性，不能只防止 `setState`。
- 返回不是网络撤销：服务端仍可能消耗一次性码，旧 socket 按既有流程终止，不做自动重试。busy 时返回按钮附近显示“返回不会撤销已发出的配对请求”。用户主动重新进入后再提交同一码，按该新请求的实际响应沿用 `INVALID_CODE_TEXT` 等既有文案；不自动重放旧请求、不引入“返回专用”错误分类，旧失败不得写入新页面。
- `onSubmit` 注入实现由宿主负责其自身持久化等副作用；本组件仅保证失效后不再调用 `onPaired`/改自身 UI，不能撤销注入实现已执行的副作用。不扩展 `onSubmit` 参数或给出虚假取消保证。
- 中继 `redeemPairCodeViaRelay` 的现有超时为 15000ms；直连 `redeemPairCode` 无应用层超时。此 spec 不新增 deadline：首启直连若对端保持连接却不响应，仍可能长期显示进度；这是既有独立限制，不列为本修复已解决。失败收敛判据指请求实际 reject/close/timeout 后。

## 5. 组件与契约修改

### 5.1 `PairingScreen.tsx`：配对状态的唯一拥有者

- 在统一兑换入口使用同步 attempt ref：只在未占用时创建尝试，占用发生在任何回填/错误修改/第一次 `await` 之前；持有至成功、失败或离开页面。
- `handleScanText` 必须先检查 attempt：已有请求时返回 `true` 让扫描实例收尾，**不解析、不改任何字段或错误**；否则非法码返回 `false`，合法且被准入返回 `true`。
- 扫描错误进入表单前也检查当前尝试，配对中不得被旧相机错误覆盖；实例层失效仍是第一道防线。
- 有效码状态切换执行 §4.2；渲染层同时用 `scanning && !busy` 保证覆盖层不能遮住进度。
- 返回/卸载采用 §4.5 的尝试失效规则；一次尝试后续处理只接受其自身 identity。
- 保留局部 `ErrorBoundary`，不能用“去掉错误边界”掩盖问题。

### 5.2 `QrScanner.tsx`：稳定相机生命周期

- 用 ref 保存最新 `onText`/`onError`，与既有 `ScanHost` 模式对齐。
- effect 只依赖实际相机依赖 `deps`，不依赖回调 identity；转发函数读取 ref 并透传结果接收返回值。
- `deps` 变化按对象引用判断（不深比较），允许显式销毁旧实例并重新创建；生产端当前不传 `deps`，组件测试必须保持 deps 引用稳定，只有专门测试更换依赖时才传新对象。
- 卸载时调用本实例 `stop()`；回调刷新不应重建实例。
- 不仅用 `useCallback` 修父组件：生命周期的稳定性由真实相机组件自身保证。

### 5.3 `qrScanner.ts`：结果接收与停机

把结果回调从 `(text: string) => void` 扩为 `(text: string) => boolean | void`：

| 返回值 | 语义 | 扫描器行为 |
|---|---|---|
| `false` | 本帧不是可接受结果 | 保留轨道和定时器，继续扫描 |
| `true` | 结果已接收 | 停止本实例，不再送后续帧 |
| `undefined` | 兼容旧 void 回调，视为接收 | 保留原先命中即停的语义 |

- 解码出文本后先把结果交给同步回调判断；仅在返回值不为 `false` 时停机。回调是同步契约，不引入异步结果判断。
- 若结果回调抛错，停止本实例并通过 `onError` 收敛一次，不把异常留在 interval 中反复触发。
- 成功送出的接收结果与相机错误互斥；接受结果后的迟到 `play()` rejection 不得再报相机错误。
- `stop()` 先标记实例失效，再清定时器和停止本实例轨道；重复调用无副作用。
- `getUserMedia` 在 stop 之后才 resolve：只停止迟到流，不赋给 video、不播放、不解码、不通知 UI。
- stop 后的取流/播放 rejection 静默忽略，不调用旧 `onError`。
- 正在运行的取流/播放失败仍按现有相机不可用路径报告一次。
- 若清理 `video.srcObject`，仅在其仍等于本实例 stream 时置空，旧实例不得清空新实例的视频流。

以上异步隔离用实例局部的 `stopped` 即可完成，不新增全局扫描 session 或状态库。

### 5.4 测试接缝兼容

`qrScanner.ts` 导出唯一类型 `ScanResultHandler = (text: string) => boolean | void`。`QrScannerProps.onText`、`PairingScreenProps.scan` 的文本回调以及 `ScanHost` 的转发复用该类型；旧注入实现仍可忽略返回值，但新测试必须验证真实扫描器的 `false`/`true` 行为。`ScanHost` 转发不能吞掉返回值。

`ScanHost` 的每次 effect 必须有局部 active 位：文本转发返回值不为 false 时立即置为 false，后续文本返回 true 但不再调用 UI；错误在当前 active 时也先置为 false，再上报一次。cleanup 先置为 false，再调用注入实现的 stop。注入实现可能在 scan 调用中同步给结果，此时尚拿不到 stop；active 必须已经关闭，拿到 stop 后正常由 cleanup 释放。旧文本回调失效时返回 true，旧错误直接忽略。如此与真实扫描器的“首个接受结果或失败即终止”规则对齐，防止同步重入/迟到消息污染新的扫描。

## 7. iOS 真机验收

验收包必须包含实际前端修复，记录源码 commit、App 版本/build、机型、iOS 版本、首次授权或已有授权、直连或中继；不能只重建原生壳而继续使用旧 dist。

| ID | 操作 | 通过判据 |
|---|---|---|
| I01 | 正常中继配对：已有预览后对准有效码 | 识别后退出相机页、进入主界面；请求仍 pending 时进度可见，立即成功不强制看到进度帧；不出现等待网络的空黑屏 |
| I02 | 建立可控慢响应（例如 3 秒） | 整个等待期间表单进度可见，无相机重复启动；不要求无限黑屏后自动恢复 |
| I03 | 过期/已用码、桌面不在线/网络失败 | 显示正确错误并恢复可编辑表单，允许重新扫码；不误报为相机权限失败 |
| I04 | 先扫普通网页码，再移向有效码 | 预览持续工作，提示无效二维码；不重新取流，随后可以完成配对 |
| I05 | 扫描中返回、再次扫码，重复 5 次 | 每次可返回、预览可恢复；相机权限/指示状态最终释放，没有旧错误影响新一轮 |
