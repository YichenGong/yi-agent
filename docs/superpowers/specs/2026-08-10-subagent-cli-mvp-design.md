# Subagent CLI MVP Design

**Date:** 2026-08-10

**Status:** approved for written specification review

## Objective

Deliver the first user-runnable vertical slice of the durable subagent runtime:
a user starts a coding session from the CLI, a daemon-owned root agent delegates
work to one child, the child produces a commit from an isolated Git worktree,
and the user accepts, requests rework, or rejects that exact delivery through
typed daemon IPC.

This MVP changes implementation order, not final scope. TUI completion,
root-child-leaf delegation, schedules, and the remaining recovery and
observability acceptance criteria stay in the full runtime milestone after the
vertical slice works.

## User Workflow

```text
yi-agent daemon start
yi-agent agent start "implement the requested change"
yi-agent agents
yi-agent agent show <child-task-id>
yi-agent agent diff <child-task-id>
yi-agent agent accept <child-task-id> --yes
```

The equivalent review alternatives are:

```text
yi-agent agent rework <child-task-id> "add the missing regression" --yes
yi-agent agent reject <child-task-id> "the change is outside scope" --yes
```

`agent start` prints the durable root session ID and root task ID. The root
worker receives the objective and may use its existing `spawn_agent`,
`send_message`, and `wait_agent` tools. `agents`, `show`, `events`, `mailbox`,
and `diff` remain the observable control surface while work is running.

## Runtime Boundaries

### Session Admission

The CLI sends one typed start-session request rather than issuing an
uncorrelated `CreateSession` followed by `StartWorker`. The daemon atomically
creates the durable root task with its objective and either admits the root
worker or returns a typed failure that leaves a coherent retryable or terminal
state. Repeating a failed CLI transport request must not silently create an
extra session; the request carries an idempotency key generated by the client.

The daemon never starts implicitly. If its socket is unavailable, the command
fails with the existing `yi-agent daemon start` guidance.

### Worktree Ownership

The user checkout is a read-only source of the selected committed base. A
coding session requires a clean Git checkout. The daemon creates:

```text
user checkout (never written by the runtime)
  root integration worktree and branch
    child delivery worktree and branch
```

The root worktree is created from the user checkout's recorded HEAD. A child
worktree is created from the direct parent's recorded clean HEAD. Branch names
and paths derive only from daemon-generated session/task IDs, never from raw
objectives. The daemon persists repository root, worktree path, branch, direct
parent branch, and base commit before starting the corresponding worker.

Every worker receives its own persisted workspace path. Built-in filesystem
and shell tools, recovery inspection, Git evidence collection, and nested
delegation all use that same path. The global daemon configuration directory
must not be reused as every worker's workspace.

Dirty or non-Git source checkouts fail before worker/provider side effects.
The runtime never stashes, copies, resets, force-removes, or writes the user
checkout.

### Commit Delivery

When a non-root coding worker finishes a successful Agent turn, the worker
factory inspects its assigned worktree through the trusted worktree service.
A valid delivery requires:

- a clean worktree;
- the expected child branch;
- a HEAD different from the recorded base;
- the recorded base to be an ancestor of HEAD;
- a commit still reachable at the exact inspected HEAD;
- non-empty verification evidence collected from the task contract/runtime.

The factory then reports a real `DeliveryReport` containing the pinned commit,
base, workspace lease, and evidence. It must not report
`CompletedWithoutDelivery` for a coding child that is expected to deliver a
commit. A dirty tree, missing commit, branch mismatch, or invalid ancestry is a
durable task failure with retained worktree evidence, not a successful empty
delivery.

Root completion is different: its integration branch is the session result and
is not automatically merged into the user checkout. The CLI reports the root
branch/worktree for explicit later user validation.

### Review And Integration

`accept`, `rework`, and `reject` encode one typed `Review` IPC request. They
operate only on the delivery currently named by `AwaitingParentReview`; a stale
delivery ID or changed child HEAD is rejected.

Acceptance has two distinct durable facts:

1. the local user approves the pinned delivery;
2. the trusted daemon integration service merges that exact commit with
   `merge --no-ff` into the direct parent's worktree and records successful
   validation evidence.

The task becomes accepted only after both facts succeed. Approval alone wakes
or notifies the direct parent but cannot claim integration. The integration
service verifies parent ownership, the recorded base, parent cleanliness,
child cleanliness, and the pinned child HEAD immediately before merging. It
then runs the MVP validation command configured by the task contract; for the
initial vertical slice this is at least `git diff --check`. A merge or
validation failure is recorded with Git evidence and leaves the relevant
worktrees intact. It never resets a successful merge silently.

Rework persists feedback, starts the successor attempt through the existing
controlled recovery/admission path, and delivers the durable feedback message
exactly once after worker admission is unambiguous. If the parent HEAD has
moved, the successor uses a fresh child worktree from the new parent base; old
history remains retained.

Reject records the reason and terminal review state and retains the child
worktree. Neither accept, rework, nor reject merges anything into `main`.

### Recovery And Failure Semantics

The existing controlled recovery gate remains authoritative. On daemon restart,
workspace identity, worktree identity, checkpoint state, registered tools, and
Git HEAD/status must attest before a recovered worker receives tools or invokes
the provider.

Before building the vertical slice, the current review checkpoint must close
two known correctness gaps:

- ambiguous rework fallback must release or durably invalidate the SQLite
  `resident:*` lease even when persisting `RecoveryRequired` also fails;
- a post-admission worker factory failure must retain the concrete factory
  error in terminal evidence while closing the attempt as failed.

These fixes are prerequisites because the MVP exercises the same admission,
rework, and restart paths.

## CLI Behavior

The first usable surface is CLI-only. Existing commands remain stable, with
these additions/connections:

- `yi-agent agent start <objective>` creates and starts a root coding session;
- `yi-agent agent accept <task-id> --yes` performs user approval followed by
  trusted direct-parent integration;
- `yi-agent agent rework <task-id> <feedback> --yes` requests a successor
  attempt;
- `yi-agent agent reject <task-id> <reason> --yes` rejects and retains it.

Review commands without `--yes` render a preview containing the task,
delivery ID, base/head, branches, worktrees, changed files when available, and
the exact action. They make no mutation. Confirmation is bound to that delivery
and expires; a changed task or delivery requires a new preview.

Human output is concise. Machine-readable output continues to use versioned
typed IPC data rather than parsing rendered strings. Unsupported or unavailable
states return the existing stable error categories.

## Permissions

The MVP does not bypass application permissions. A daemon-owned worker uses the
same permission policy as the application Agent. Requests that require a local
user decision are persisted and resolved through the existing typed
`ResolvePermission` path before tool execution continues. `--yolo` retains its
existing explicit semantics; the daemon must not infer it from being detached.

A full TUI permission card is post-MVP, but pending request IDs and decisions
must be observable and resolvable from the CLI so a worker cannot hang forever
without an actionable identifier.

## End-To-End Verification

The deterministic MVP test uses a temporary Git repository and mock providers;
it does not call a real LLM API. It proves this sequence:

1. initialize and commit a clean user checkout;
2. start the daemon with a scripted root provider;
3. invoke the CLI start request with a coding objective;
4. root calls `spawn_agent` and waits;
5. child writes only its assigned worktree, commits, and completes;
6. daemon emits `AwaitingParentReview` with a real pinned delivery;
7. CLI inspection exposes the child diff and delivery identity;
8. CLI accept merges the pinned child commit into the root integration
   worktree with a merge commit;
9. the user checkout and its branch/HEAD remain unchanged;
10. SQLite records approval, integration evidence, terminal state, and released
    resident ownership;
11. restarting the daemon preserves inspectable state and does not replay the
    accepted delivery.

Separate deterministic paths prove rework feedback reaches the successor
attempt and reject retains an unmerged child worktree. Failure tests cover a
dirty source checkout, no child commit, changed reviewed HEAD, merge conflict,
validation failure, permission denial, daemon absence, and restart recovery
conflict.

## MVP Completion Boundary

The MVP is complete only when the CLI workflow above runs against the real
daemon and real Git operations, the deterministic end-to-end tests pass, and
the focused core/store/tools/application suites pass serially. Unit tests that
invoke the coordinator directly are supporting evidence but cannot substitute
for the CLI-to-daemon-to-worker-to-Git end-to-end test.

The following remain required for the full subagent-runtime milestone but do
not block this first runnable slice:

- complete TUI task tree, review, and permission interactions;
- root-to-child-to-leaf end-to-end delegation and direct-parent integration;
- natural-language schedules executing the same worker pipeline;
- all remaining checkpoints 1-20 audit items;
- strict Clippy and project-management updates;
- final user validation and an explicitly authorized merge decision.

No MVP operation merges the feature branch or any runtime integration branch
into `main`.
