# Superpowers 看板插件设计

**日期：** 2026-09-30
**状态：** 设计已确认，待评审
**模块：** `yi-agent-kanban`（独立插件进程）+ `kanban` system skill + 两端 UI + 设置开关

---

## 1. 背景与问题

用户是管理者，不能持续盯守编码环境。已使用的大模型服务随时段变化限流：

- 工作日 09:00–24:00：800 req/h（≈ 最多 3 个任务并发）
- 工作日 00:00–09:00：不限流
- 周六、周日：不限流

诉求：把**已决策完成的需求**（一对 spec + plan 文件）排成队列，按时段并发上限自动往下
执行，尽量打满机器；用户不需要监控每一个任务，只在真正需要决策时才介入。

因为该方案高度个性化，它必须：

1. 作为插件存在，不与主流程耦合，保证主流程干净；
2. 因是特化方案，允许与 Superpowers 的业务流程（SDD）强绑定。

## 3. 范围边界

**做什么（插件侧，独立可安装/卸载）：**

- 新增**独立进程** `yi-agent-kanban`：卡片模型、队列状态机、时段并发日历、队列推进决策、
  看板存储（自己的 SQLite，不碰 daemon 的库）。
- 该进程通过 daemon 既有 IPC 创建会话、启动、订阅状态；到点推进队列。
- 新增 `kanban` system skill（纯提示词，可独立装卸）：约束执行者按 Superpowers 规范
  自建 worktree、执行 spec+plan、呈现合并菜单、卡住时报告 BLOCKED。
- **两层设置开关**（全局默认 + 项目覆盖）与设置界面：desktop 设置入口、TUI `/kanban`
  开关项、Web 配置页一组。
- desktop 看板视图；TUI `/kanban` popup。

**做什么（daemon 侧，仅一处通用能力）：**

- 补上「**创建一个自主的、带独立 worktree 的、可写的会话，并驱动到底**」这一通用能力。
  该能力**不含任何 kanban 专属逻辑**，任何自主场景都可复用；它是当前架构唯一真正缺失的
  一环（见 §5）。

**不做什么：**

- 不做请求级限流计数（沿用任务级并发；429 由既有退避兜底）。
- 不做自动合并、不替用户执行 `git merge`。
- 不做跨项目看板。
- 不做看板内的需求讨论/草稿态（方案 A：提升时两文件已存在）。
- 不改既有任务树、审核、交付、worktree 回收语义。
- 不做 TUI 的会话时间线跳转（第一版）。

## 4. 架构

```
┌──────────────── 用户会话（讨论需求） ────────────────┐
│  普通 Thread：brainstorming → spec + plan 文件       │
│  动作：「加入看板」→ 校验两文件成对 → 入队            │
└───────────────────────────┬──────────────────────────┘
                            │ IPC: EnqueueCard
                            ▼
┌──────────── yi-agent-kanban（独立进程，可装卸）──────┐
│  看板队列（自有 SQLite，与 daemon 库分离）            │
│    ├─ 卡片状态机（§6）                                │
│    ├─ 时段并发日历（§7）                              │
│    └─ 推进循环：                                      │
│         选队首 → 经 IPC 请求 daemon 建自主会话并驱动   │
│                                                       │
│  卸载 = 停进程 + 删目录；yi-agent 主程序零改动         │
└───────────────────────────┬──────────────────────────┘
                            │ IPC（既有协议 + 一处通用新增）
                            ▼
┌──────────────────── 常驻 daemon ─────────────────────┐
│  新增通用能力：创建"自主可写会话"并驱动到底（§5）      │
│                                                       │
│  现有能力（复用，不改语义）：                          │
│    任务树 / 状态机 / WatchdogLimits / 资源租约         │
│    事件流 / worktree 回收 / 审核                       │
└───────────────────────────┬──────────────────────────┘
                            │ IPC: 只读订阅事件流
              ┌─────────────┴─────────────┐
              ▼                           ▼
      desktop 看板视图              TUI /kanban popup
      （可点开看时间线）            （状态/进度/证据，只读）
```

**为什么 daemon 必须补一处能力（诚实说明）：** 当前 daemon 只有在被显式调用
`StartWorker` / `spawn` / `retry` 时才会启动 worker（`runtime.rs:1268/1772/1989/2414`）；
定时任务只创建 root 会话记录（`evaluate_schedules`），**之后没有任何东西把它跑起来**——
`IpcRequest::StartWorker` 在生产代码里零调用方。更关键的是，**根会话被强制为 ReadOnly**
（`attach_application_root` 注释："A root never provisions a worktree: it runs in the project
directory"），没有 write/edit 工具，也没有独立 worktree。因此「创建一个自主的、带独立
worktree 的、可写的会话」这一环在现有机制里**不存在**，是本方案唯一的 daemon 侧新增；
而会话/任务/attempt/状态机/worktree 回收等骨架全部现成。

## 5. 执行体的精确语义（方案 X + P-B）

一张卡片在队首启动时，**由 kanban 进程发起、daemon 执行**：

1. kanban 进程经 IPC 请求 daemon 创建一个**自主可写会话**（daemon 侧新增的通用能力）：
   - 以 **Coding 模式**建立 root session（现有 `create_session_with_objective_and_mode`
     只支持 ReadOnly 根，这里需要扩展为可写根）；
   - 由会话自己按 Superpowers 规范在自己的独立 worktree 中工作（§8）；
   - daemon **自动启动并驱动到终态**（补上缺失的 worker 启动驱动）。
2. root 的 objective 由 kanban 模板生成（§8），指向 spec/plan 文件。
3. 会话结束后，kanban 进程读其终态与交付证据，把卡片推进到 `awaiting_merge` 或
   `needs_you`。

**这一处 daemon 新增是通用的：** 它回答的是「给我一个自主可写、有独立 worktree、能自己跑
到底的会话」，不包含卡片、队列、并发日历、Superpowers 等任何 kanban 概念。任何未来的
自主执行场景都能复用同一个入口。

**与 desktop thread 的区别（必须在文档里说清）：**

- desktop 侧边栏的 thread 由 **app-server 进程**托管，App 退出即不再被驱动。
- 卡片对应的执行会话由 **daemon** 托管，无人值守时仍继续跑（前提是 daemon 常驻）。
- 因此**两者是两套持久化**，卡片会话不会自动出现在侧边栏；它只通过看板视图可见。

**幂等要求：** 创建会话与启动驱动必须幂等——同一卡片同一次启动不得创建两个会话或两个
worker。以 daemon 持久化状态为准（复用 `has_worker` 检查），而不是 kanban 进程的内存。

**卸载语义：** 停掉 kanban 进程、删除其数据目录即可。**不影响已在 daemon 中运行的会话**
（它们会正常跑完）；也不影响 daemon 与既有前端的功能。

## 6. 卡片状态机

```
queued ──▶ running ──▶ awaiting_merge ──▶ done
   │          │  ▲
   │          ▼  │
   │      needs_you ──▶ failed
   │
   ├──▶ paused ──▶ cancelled
   │
   └────────────────▶ cancelled
```

| 状态 | 含义 | 占用槽位 |
|------|------|----------|
| `queued` | 排队中，等槽位 | 否 |
| `running` | 正在执行 | **是** |
| `needs_you` | 需要用户决策（BLOCKED / plan 冲突 / 预算耗尽） | 否（立即释放） |
| `awaiting_merge` | 执行完成，分支上有 commit，等用户决定集成 | 否 |
| `failed` | 终止性失败 | 否 |
| `done` | 已集成 | 否 |
| `paused` | 用户主动暂停，保留位置但不再被推进 | 否 |
| `cancelled` | 用户主动取消（终态） | 否 |

**`paused` / `cancelled` 的由来：** 看板是用户的管理界面，用户必须能「叫停」一张排在队伍里
的卡片而不必删除它（`paused`），以及在确定不做时彻底移除（`cancelled`）。二者都**不是**
执行结果，只由用户操作产生；`cancelled` 是终态，`paused` 可被用户重新放回 `queued`。

**不变量：**

- 任意时刻 `running` 卡片数 ≤ 当前时段上限。
- **只有 `running` 占用槽位**（`queued` / `needs_you` / `awaiting_merge` / `failed` /
  `done` / `paused` / `cancelled` 都不占用）。
- 卡片进入 `needs_you` 或 `awaiting_merge` 后，队列立即推进下一张。
- 卡片进入 `needs_you` / `awaiting_merge` / `failed` / `done` / `paused` / `cancelled`
  时若正持有槽位，必须**立即释放**，队列不得空转。
- 关闭看板开关**不改变**任何卡片状态，也不取消已在 daemon 中运行的会话（§12）。

## 7. 时段并发日历

插件配置（拟 `<workdir>/.yi-agent/kanban.toml`）：

```toml
default_max_tasks = 3

[[window]]
days = "Mon-Fri"
start = "09:00"
end = "24:00"
max_tasks = 3

[[window]]
days = "Mon-Fri"
start = "00:00"
end = "09:00"
max_tasks = 10

[[window]]
days = "Sat,Sun"
all_day = true
max_tasks = 10
```

**解析规则：**

- 给定本地时刻 → 命中第一个匹配窗口 → 取 `max_tasks`；无命中取 `default_max_tasks`。
- 边界以本地时区为准；`end` 为开区间（`24:00` 表示到当日 23:59:59）。
- 配置缺失/损坏 → 回退 `default_max_tasks = 3`（保守），并记 warning；绝不因配置错误停摆。
- 时段切换（如 09:00 从 10 降到 3）**不打断**正在运行的卡片；只影响新启动，直到运行数
  自然回落到新上限以下。

**为什么不做请求级计数：** 用户明确按任务级并发（"大概同时 3 个任务在运行"）。请求级计数
是最易出错、最脏的部分；且现有 `max_llm_requests_per_provider_key` 策略字段并未真正接到
调度器上（容量是硬编码常量 `DEFAULT_LLM_PER_PROVIDER_KEY`），依赖它反而更不可靠。若某时段
3 个任务仍打出 429，由既有 `RetryFailure::ProviderRateLimited` 指数退避 + 抖动兜底。

## 8. 执行者约束：kanban skill

插件为卡片 root 注入 objective 模板，约束执行者遵循 Superpowers 规范：

1. 在**插件已预建好**的隔离 worktree（`.worktrees/kanban/<卡号>-<slug>`，
   分支 `kanban/<卡号>-<slug>`）中工作——见下方「worktree 归属」；
2. 用 `superpowers:executing-plans` / `superpowers:subagent-driven-development` 执行
   spec + plan；
3. 结束时用 `superpowers:finishing-a-development-branch` **呈现选项**，**绝不自动合并**；
4. 遇到无法解决的阻塞 → 报告 BLOCKED（插件将其映射为 `needs_you`）。

**worktree 归属（按「插件预建」落地）：** 插件在启动一张卡片前，用**纯 `git worktree add`**
（本地操作，**不消耗任何模型调用**）建好 `.worktrees/kanban/<卡号>-<slug>`，把该路径作为
`workdir` 传给 daemon 的自主会话，并写入 `Card::workdir` 供控制面展示。

为什么不让执行者自建：并发启动多张卡片时，若由模型自己建 worktree，每次都要花一轮模型调用
去执行 `using-git-worktrees`；在建 worktree 这种纯机械步骤上消耗额度，与「打满机器但限流」
的目标冲突。插件预建让并发启动只需本地 git 操作，额度全部留给真正的编码工作。
执行者仍**必须**在该 worktree 内工作，并**仍然遵守** `superpowers:using-git-worktrees` 的
其余规范（分支命名、隔离要求、结束时呈现选项而非自动合并）。daemon 侧保持「只观察、不创建目录」。

**控制面数据来源：`board.json`（文件即契约）。**

插件每个调度 tick 结束后，把队列状态原子写入插件自己的状态目录
`<state-dir>/board.json`（临时文件 + rename）。TUI 与 desktop **只读这个文件**渲染看板：

- 卡片行：`id`、`state`、`workdir`（即「跑在哪里」）、队列顺序；
- 文件缺失/损坏/字段缺失 → 控制面回退为空列表，**绝不 panic**，也**绝不**因此让前端不可用。

这样选择的理由：控制面是**宿主**的一部分（spec §13），而看板数据属于**插件**。用文件做契约，
两边不需要新增 IPC、不需要互相链接，插件删掉即卸载，控制面只是「读不到文件 → 空看板」。
daemon 的 runtime 库完全不知情（§13 数据分离）。

**进度可观测（不需要询问模型）：**

- plan 文件的 task 勾选状态；
- SDD 账本 `<repo>/.superpowers/sdd/<plan-basename>/progress.md` 中的
  `Task <N>: complete` 行与 fix round 行。

两者结合得出 "3/7 tasks" 之类的进度。

## 9. 创建卡片（提升）

流程：

1. 用户在普通会话中讨论需求，产出 spec + plan 文件（沿用项目既有规范路径：
   `docs/superpowers/specs/` 与 `docs/superpowers/plans/`）。
2. 用户执行「加入看板」（slash command / 界面动作），指定 spec 路径与 plan 路径。
3. 插件**校验两文件成对存在**（判据是文件存在，而非模型声称完成）。
4. 校验通过 → 入队为 `queued`；失败 → 拒绝并给出明确原因。

讨论与看板彻底解耦：讨论是高度交互的过程，且**不占用任何队列资源**。

## 10. 控制面

### 设置开关（两层）

名称统一为 **Superpowers 看板**。开关为**完整功能开关**：关闭时该功能的 UI 入口、
slash 命令、插件进程推进全部隐藏与停止，形同不存在；重开即恢复。

**两层解析（项目覆盖全局）：**

| 层 | 落点 | 语义 |
|----|------|------|
| 全局默认 | `~/.yi-agent/preferences.json`（新建） | 对所有项目生效的默认开关 |
| 项目覆盖 | `<workdir>/.yi-agent/preferences.json`（复用现成机制） | 仅覆盖本项目；缺省则继承全局 |

- 解析规则：项目层显式设置则用项目层；否则用全局层；两层都缺失则**默认关闭**（新功能
  保守默认，不会在用户不知情时自动跑队列）。
- 写入复用现有项目级偏好的写法（临时文件 + rename 原子替换；损坏一律回退默认并记 warning）。
- 全局层是**新增落点**：现有代码只有项目级 `preferences.json`（`tui/runtime_prefs.rs`），
  没有全局偏好文件，因此需要新建一个同构的全局读取/写入路径。

**关掉时到底发生什么（精确语义）：**

1. 看板 UI 入口（desktop 视图、TUI `/kanban`）隐藏；
2. 插件进程不再推进队列（新卡片不启动）；
3. **已经在 daemon 中运行的卡片会话不被杀死**——它们归 daemon 管，会正常跑完；
4. 看板数据保留，重开后队列与状态原样恢复。

**设置界面落点：**

- **desktop**：新增设置入口（侧边栏/菜单），内含"Superpowers 看板"开关（项目级），
  并可显示/修改全局默认。
- **TUI**：`/kanban` 内的开关项；另可在 `/config` 显示当前生效值与来源（全局 / 项目）。
- **Web 配置页**（`yi-agent web`）：增加"Superpowers 看板"一组，管理全局与项目两层开关。

### desktop

- 看板视图（与 `ThreadSidebar` 并列，不替换）。
- 卡片列表：状态、进度、所属项目、等待时长。
- 卡片详情：spec/plan 链接、commit 列表、变更统计、验证结论、分支名。
- 操作：插队、调整顺序、暂停/恢复、取消、"打开执行会话"（只读订阅事件流）。

### TUI

- `/kanban` slash command → popup（复用 `/agents` 的 `ListPopup` / `DetailPopup` 范式）。
- 可见：状态、进度、证据（commit / 验证结论）。
- **降级：** 不做跳转查看完整会话时间线（TUI 目前只有单一根会话，无多会话读路径）。

### 合并（Q7-a）

看板**不执行**合并。卡片进入 `awaiting_merge` 时展示证据并提供入口；用户进会话，由
`finishing-a-development-branch` 走正规菜单（合并 / 提 PR / 保留）。

## 11. 测试策略

**插件侧（`yi-agent-kanban` 进程，可独立测试）：**

- **并发日历单测：** 给定本地时刻 → 正确上限；覆盖工作日跨时段边界（08:59 / 09:00 /
  23:59）、周末、配置缺失与损坏回退。
- **队列状态机单测：** 槽位获取/释放/补位；`needs_you` 不阻塞队列；FIFO 与插队；
  暂停/恢复/取消；状态转换不变式（`running` 数 ≤ 上限）。
- **推进幂等单测：** 同一卡片重复推进不产生第二个会话或 worker。
- **提升校验单测：** spec/plan 缺失或不成对时拒绝入队。
- **开关解析单测：** 项目层覆盖全局；两层缺失 → 默认关闭；任一文件损坏 → 回退默认不崩溃；
  关闭时队列不推进、UI 入口隐藏；关闭**不杀死**已在 daemon 中运行的会话。
- **可装卸验证：** 删除插件目录后，daemon 与既有前端功能不受影响。

**daemon 侧（通用能力）：**

- **自主可写会话单测：** 能创建一个 Coding 模式、带独立 worktree 的根会话，并自动驱动
  到终态；非 git 项目与不可写路径有明确失败。
- **端到端：** 临时 SQLite + socket，验证"插件请求建会话 → daemon 自动跑完 → 终态与交付
  证据可读"。不调用真实 LLM。

## 13. 插件形态与解耦边界

`yi-agent` 目前**没有动态插件机制**（无 dylib/dlopen/加载器），因此"可独立安装/卸载"
只能通过**独立进程**达成。这也是本方案选择 P-B 的原因。

| 组件 | 形态 | 独立安装/卸载 | 归属 |
|------|------|--------------|------|
| `yi-agent-kanban` 进程 | 独立可执行文件 + 自有数据目录 | **是**（放/删文件 + 起/停进程） | 插件 |
| `kanban` skill | 纯提示词目录 | **是**（放/删目录） | 插件 |
| desktop / TUI 看板视图 | 各自前端内的一块 UI | 否（随主程序编译） | 宿主 |
| 设置开关（两层偏好） | 全局 `~/.yi-agent/` + 项目 `<workdir>/.yi-agent/` | 否（宿主偏好机制） | 宿主 |
| daemon「自主可写会话」能力 | 一处通用 IPC + 会话启动路径 | 否（属于 daemon） | **通用宿主能力** |

### 解耦如何保证

1. **业务逻辑全在插件进程内**：卡片、队列、状态机、并发日历、Superpowers 约束、看板
   存储，daemon 一概不知。
2. **daemon 侧只加一处通用能力**：语义是「创建并驱动一个自主可写的隔离会话」，可被任何
   场景复用，**不含 kanban 概念**。它不是插件逻辑，而是宿主补齐的一块基础设施缺口。
3. **数据分离**：插件有自己的 SQLite，与 daemon 的 runtime 库互不写入。
4. **卸载安全**：停进程 + 删数据目录。正在 daemon 中运行的会话会正常跑完；主程序功能
   不受任何影响。
5. **不改既有语义**：任务树 / 审核 / 交付 / worktree 回收 / 既有 IPC 行为一律不动。

### 诚实的残余耦合

插件依赖 daemon 存在且常驻（这是"无人值守"的前提）。daemon 不常驻时，看板无法推进队列
——这不是插件能自行解决的，属于既有运行时的部署前提。

### 为什么不做成编译期内置 crate

如果做成 workspace crate，它就**不能独立安装/卸载**，必须随主程序一起编译发布。这与用户
"可独立安装、可卸载"的要求直接冲突，因此不采用。
