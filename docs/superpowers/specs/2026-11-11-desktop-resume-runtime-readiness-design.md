# Desktop 历史会话运行环境准备与显式恢复设计

日期：2026-11-11。

用户已同意修复方向：本地冷会话恢复前等待项目准备就绪；提供一次明确的准备并恢复操作；保留授权门禁、历史与草稿，不自动发送。本文是实施前的书面设计，尚不代表代码修复完成。

## 1. 已知事实与诊断边界

- 当前安装的 sidecar 日志报告版本 `0.1.13-dev+7e590b96`。
- `~/.yi-agent/trace/session-20261111-094739.jsonl` 在 09:48:41Z、09:48:44Z 报告 `stage=attach_root`，原因是项目 runtime `not lifecycle-ready`；另一个项目出现授权应答超时。这些是不同的失败，不能统一认定为启动竞态。
- `DesktopRuntimeManager::is_lifecycle_ready` 要求当前项目 `state.ready` 且 `lease_is_live`；`authorize_intent` 不满足时拒绝 root 授权。
- `App.tsx` 新建本地会话先等待 `prepareRuntimeProject`，冷恢复直接请求 `thread/resume`；`useRuntimeLease` 根据当前项目另行异步申请租约，两条路径没有显式就绪屏障。
- 当前横幅重试负责项目准备，而重新选择会话负责再次恢复，用户需要完成两个独立动作。
- 日志只证明授权时未就绪，尚不能区分准备失败、未完成或租约失效。本轮必须增强诊断，不能声称已查明所有底层失败原因。

## 2. 范围与非目标

适用范围为本地桌面壳持有的会话运行环境。远端浏览器与远端槽位保持现有恢复协议，不调用本机准备命令。

不修改 guardian 授权规则，不将 blocked/unknown/starting 当成功，不降级 embedded，不自动确认版本切换或 legacy 接管。不删除 runtime 数据、不重跑历史 child、不自动重发消息、不替用户停止正式 App 或部署安装包。

## 3. 恢复顺序

1. 保留现有会话选择与缓存显示。运行中或等审批会话仍走只读 `thread/readItems`，不能为了准备环境而进入会中断 turn 的 `thread/resume`。
2. 仅对确实需要冷恢复的本地会话执行项目准备。项目路径使用已有会话元数据；元数据缺失时先从现有列表/元数据解析，不猜测当前进程 cwd，不拿别的项目替代。仍无法确定路径时明确阻止本地激活并可重试。
3. 同一会话的准备和恢复共用一次在途激活，连续点击不会创建重复恢复。复用现有项目租约准备入口和原生每 scope 单次准备机制，后台租约申请与显式准备不能互相覆盖新结果。
4. 只有准备应答明确为 `managedReady` 后才发起本次 `thread/resume`。应答为 null、starting、blocked、unknown、legacyChoiceRequired 时保留阻断，展示现有固定状态文案。
5. 准备前后分别验证客户端、槽位、会话对象和选择版本。用户切换或删除会话、重连、切换槽位后，旧准备结果不能继续发起恢复，也不能更新新会话的错误状态。
6. 已开始的恢复保留现有 historyFirst 协议和 request token 关联。历史完成不等于激活完成；只有恢复成功才能置 warm 并解除激活发送门禁。
7. 环境准备等待不计入历史回放停滞计时；历史 watchdog 从真正开始回放时管理。准备阶段仍须有明确的在途状态，防止发送越过准备屏障。

缓存正文立即可读；没有缓存且准备未完成时，不额外引入全量历史协议或把未收到的正文标记已同步。保留现有“有历史可读”与“可运行”两个事实的区别。

## 4. 失败与一次显式恢复

- 项目准备失败不清空历史、草稿、附件，不设置 warm，不发起 turn；激活失败不伪装成历史损坏。
- 当前本地会话遇到准备或激活失败时，提供“准备运行环境并重试”操作。该操作先重新准备项目，成功后恢复原会话，不要求用户手动切走再切回。
- 横幅的项目准备重试与会话激活恢复协调：只有操作发起时绑定的当前失败会话满足同项目、客户端、槽位、选择版本条件，准备成功才继续恢复。不能恢复后来选择的其他会话。
- 新建会话被准备门禁拦截时，原有重试仍只准备项目，不自动创建会话。
- 对运行中/等审批会话不提供会中断任务的恢复动作；重复点击、迟到应答不能导致重复恢复。
- 重试成功清除激活错误；失败保留可重试入口及状态。没有项目准备 issue 但 root 激活失败时，恢复入口也必须可见，不能依赖项目横幅恰好存在。
- 所有恢复操作只恢复环境，不保存待发送队列。操作前失败的发送意图不在恢复后自动执行；草稿保留供用户显式发送。原有正常激活等待发送行为不扩大到失败恢复路径。

## 5. 原生诊断与权限边界

在原生拒绝 root 授权处记录结构化诊断，区分：没有项目状态、准备未就绪、已记录就绪但实时租约失效。

允许记录 scope、attempt id、固定 acquire state、held、ready、记录的 daemon generation 和本次实时租约检查结果。不新增无关状态查询，不重复触发有副作用的租约检查，不记录 capability、generation secret、management secret、token、完整请求或用户正文。

前端继续使用固定文案表，不直接显示原生原始 authority 错误。保留客户端、sidecar epoch、scope、有效租约等现有授权检查。准备成功后到授权前失效的情况仍拒绝，并允许用户重新准备；不以一次旧的 managedReady 应答作为永久授权。

本轮不在 `authorize_intent` 内自动启动或无限等待 runtime，避免把准备副作用和权限准入混在一起。如诊断确认另有底层故障，单独记录确切条件后修复，不放宽门禁或盲目增大超时。

## 6. 验收矩阵

1. 本地冷恢复的准备 Promise 未完成时不发送 `thread/resume` 或 `turn/start`；缓存正文、草稿仍可见。
2. managedReady 后恰好一次恢复；准备失败或非 ready 状态不恢复，展示稳定状态。
3. 切换会话/槽位、删除会话、重连后旧准备结果不发起恢复、不覆盖新状态；晚到租约由既有租约机制处理。
4. 准备和恢复期间重复点击不重复发起工作；正常后台租约获取与显式准备可共存且不覆盖较新结果。
5. 准备慢于历史 watchdog 时不误报内容加载超时；恢复开始后的真实历史停滞仍有界失败。
6. 历史已完成而 root 激活失败时历史保持已同步，发送被拦截，恢复入口可见。
7. 点击恢复入口先准备后恢复；准备失败不继续，成功后清除激活错误；不清草稿/附件、不自动发送、不自动创建会话。
8. 本地运行中和等审批会话只读不 resume；远端恢复不调用本机准备命令。
9. 原生测试覆盖未准备/未就绪/租约失效拒绝，并确认正常授权仍工作、诊断不泄密。
10. 前端完整 vitest 与 build；原生相关测试；Rust 格式与 worktree 内 `just ci` 全绿。代码合并后在 main 再跑 `just ci`；记录实际命令和结果，不把测试通过等同于已部署安装版。
