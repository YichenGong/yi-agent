## 1. 审查方式

1. 两位只读审查者分别核对状态/生命周期与测试/行为回归；主会话同步核实代码。
2. 对反馈先查实际代码，不机械采纳。`parsePairUri` 是同步纯函数，不存在在解析期间让出执行权的竞争；修订明确其前提，而不是在非法二维码时占用兑换准入。
3. 第一轮问题修订后，交给新的只读审查者通读全文，检查修订是否相互矛盾。
4. 最终再由主会话检查验收编号、链接、占位符和 plan 对 spec 的覆盖；只在无未解决意见时交付 plan。

## 2. 第一轮发现与处理

| 编号 | 问题/证据 | 修订与落点 |
|---|---|---|
| R01 | React 可合并立即完成请求的进度更新；要求所有成功路径必须看到进度帧不可执行 | §2 G1、§4、A01/A15、I01：pending 要可见进度，立即完成允许直接最终状态，不加 flushSync/人为等待 |
| R02 | `busy` 是渲染闭包值；仅在 await 前 setBusy 不能阻止同 tick 重复结果。仅检查兑换次数也会漏掉二次回填 | §3、§4.2、§5.1、A02：同步 attempt 检查/占用先于状态修改，已有尝试不解析、不改字段/错误；解析在准入前是同步纯函数 |
| R03 | 重配页现有 onCancel 可返回；禁止 busy 返回会新增死路，特别是无应用层超时的直连 | §4.1/§4.5、A16、I06：保留返回，先使尝试失效；不冒充网络撤销 |
| R04 | 返回后迟到成功仍可能写配置并触发 App 清缓存/切连接，仅防 setState 不够 | §4.2/§4.5：检查有效性、默认落盘、宿主通知在同一同步块，不插 await；await 后且落盘前检查 identity；通知前再次核对 |
| R05 | notice 已有 role=status，新进度若无名称测试定位不唯一 | §4.3、A01：aria-label=配对进度，按 role+name 定位；结束卸载进度节点 |
| R06 | ScanHost ref 只解决回调 identity，不阻止 cleanup 后旧回调进入新的扫描 | §5.4、A18：effect 局部 active 位，cleanup 先失效再 stop；旧文本返回 true、旧错误忽略 |
| R07 | 同步结果接缝在首次接受后、cleanup 前还可能再次给文本或错误 | 主会话追加自查：§5.4/A18 首个接受结果或错误即关闭 active，不等卸载；无效码 false 继续 |
| R08 | 旧 play/getUserMedia rejection 可在 stop 后报告相机错误，或清理新实例 video | §5.3、A09–A11/A17：失效错误静默，当前失败只报一次；若清 srcObject 只清自己流 |
| R09 | 无效码→有效码的旧错误清理、输入实际 disabled、deps 引用变化未明确 | §4.2/§4.3/§5.2、A02/A08：有效准入后清旧错，属性和同步入口同时守卫；deps 按引用判断，生产不传 |
| R10 | 只撤销“早关扫码”仍被 !busy 渲染保护挡住，不能声称 A07 必然红 | §6：A07 的回退需恢复完整旧缺陷，即同时移回 finally 与撤销 !busy 保护；A05 单独恢复回调依赖必须红 |
| R11 | App 的 mock RpcClient 不验证相机；真实组件测试需明确哪些可替换 | §6 A07/A08/A14 禁止 mock 相机组件/扫码循环；A13 只验证宿主路径；新加 A15–A18 后同步完成条件 |
| R12 | 直连无 deadline、onSubmit 自有副作用与返回后的码消耗边界容易被误读成已解决 | §4.5、I07：沿用协议/超时，不自动重试；注入副作用不承诺撤销；新尝试实际过期则沿用原文案 |
